# Career Navigator

A hierarchical (Domain → Role → Specialization → Technology) career recommendation
and discovery system built for Nepali students who don't know what career options
exist beyond the handful everyone hears about (Doctor, Engineer, Pilot...).

This document exists so you can come back and actually understand what was built,
not just that it runs. Read it top to bottom once before your viva.

## The problem this solves

Two different problems, on purpose:

1. **Career awareness** — most students only know ~10 careers exist. The **Career
   Explorer** (`/explore`) solves this: browse every domain/role/specialization,
   no quiz required.
2. **Career matching** — given your actual profile, which of the many options fits
   best, all the way down to the specific specialization and technology, not just
   "you should be a Software Developer." The **Recommendation wizard**
   (`/recommend`) solves this.

## The four-level hierarchy, and why each level uses a different method

This is the single most important design decision in the project, so understand
it before anything else.

| Level | Example | Method | Why this method and not another |
|---|---|---|---|
| **1. Domain** | Technology & Computing | Random Forest | Real aptitude signal exists — analytical thinking, math score, and stated interests genuinely relate to which broad field fits someone. |
| **2. Role** | Software Developer | Random Forest, **one model per domain** (a cascade) | Trained only on that domain's students, so it's choosing among 4-9 roles instead of all 61 — a focused, easier, more accurate problem than one flat classifier. |
| **3. Specialization** | Mobile Development — Cross-Platform | **Similarity (K-Nearest-Neighbors)**, not a trained classifier | There is no honest ground truth linking academic scores to "will you prefer Web vs Mobile development" — that's driven by exposure and curiosity, not measurable aptitude. Training a classifier here would mean inventing the label and then "discovering" it back. Instead: find the most similar real students who chose this Role, and report which specializations *they* actually picked, as a relevance score, not a prediction. |
| **4. Technology** | Flutter, Dart, Git | **Pure lookup table** (`career_taxonomy.py`), zero ML | Flutter isn't a career, it's a fact about what Cross-Platform Mobile Development uses. No model needed, no fake percentage attached. |

**K-Means clustering** sits outside this pipeline entirely — it's unsupervised
student-archetype discovery for the Data Analysis page, not part of any
recommendation decision.

## Explainability — no black box

Every recommendation includes real reasons, generated by comparing your actual
values against the *real average* of students in that Domain/Role
(`modules/explainer.py`). No SHAP, no opaque model internals — just true
statements like "your analytical thinking (5/5) matches or exceeds the average
for real students in this domain (4.3/5)."

## The dataset — and why the numbers look the way they do

`backend/data/career_data.csv` is **synthetic** — generated by
`generate_data.py` from hand-authored Domain/Role skill/score/preference
profiles, sampled with random noise. It is NOT real student survey data.
Before real deployment, Domain/Role requirements should be validated against
real outcome data (student surveys, or public occupational data like O*NET).

Two numbers are worth understanding, not just quoting:

- **Domain model: ~73% accuracy across 13 classes** (vs. ~8% random guessing,
  so ~9x better than chance). Earlier versions of the generator hit 99.8%
  accuracy — that was a **leakage bug**, not a good result: the interest-tag
  generation was too cleanly separated by domain, so the model was trivially
  reading the answer off one feature. It was deliberately fixed by adding
  realistic overlap (secondary interests, background noise) until the number
  became *credible* instead of suspiciously perfect. A model that's "too
  accurate" on a hard real-world problem is a red flag, not a win.
- **Role model accuracy varies a lot by domain (45%-87%).** This is honest,
  not a bug — telling apart Nurse vs. Pharmacist from academic scores alone
  *should* be hard, because in real life that choice depends on more than
  measurable aptitude. Reporting one clean number for every domain would have
  been the less honest choice.

## How to run it

Terminal 1 — backend:
```bash
cd backend
venv\Scripts\activate
python -m uvicorn main:app --reload --port 8010
```

Terminal 2 — frontend:
```bash
cd frontend
npm run dev
```

Then open the URL Vite prints (it auto-picks a free port, e.g. `localhost:3000`
or `3002` if others are busy).

To regenerate the dataset (e.g. after editing `career_taxonomy.py` or
`generate_data.py`):
```bash
cd backend/data
python generate_data.py
```
Restart the backend afterward — models train once and are cached in memory.

## What's expandable, and how

Only 3 of 13 domains (Technology & Computing, Finance & Business, Design &
Creative) have full Specialization + Technology depth. The other 10 stop at
Role level (`"expandable": True` in `career_taxonomy.py`). To deepen one:

1. Add a `"specializations"` dict to that role in `career_taxonomy.py`,
   following the same shape as the existing Technology entries (skills
   required, tools required, technologies list).
2. Re-run `generate_data.py` — it reads the taxonomy automatically, no other
   code changes needed.
3. Retrain by restarting the backend.

## A real bug worth understanding: why the Domain model needed two models blended, not one

Early testing found that a student's stated interests barely moved the Domain
recommendation — someone picking Healthcare/Agriculture tags could still get
back Technology or Finance. Debugging this (not guessing — testing the model
directly at each step) found **three independent, stacked causes**:

1. **Academic scores drowned out interests in a single shared model.**
   `business_score` and `computer_score` ranked far above any interest feature
   in importance, because scores have much bigger between-domain spread than
   interest tags do. Fixed by training the Domain level as two blended
   models — a full-profile Random Forest and a dedicated interest-only Random
   Forest — combined with a stated weight (`INTEREST_BLEND_WEIGHT = 0.45` in
   `ml_models.py`), the same explicit-blend pattern used for RF+KNN elsewhere
   in this kind of system.
2. **A single click registered the weakest possible signal.** The wizard's
   tag-strength cycle defaulted a first click to `1`, but genuine training
   data associates real interest with values closer to `2`. Fixed by changing
   the click cycle to skip straight to `2` on first click.
3. **Class imbalance from Specialization depth.** Technology & Computing and
   Finance & Business have far more training rows than shallow domains,
   purely because giving them Specialization-level depth also means more
   roles × oversampled rows. This gave big domains a "wins by default"
   population-size prior whenever real signal was weak. Fixed with
   `class_weight='balanced'` on both Domain-level classifiers.

On top of all three fixes, the wizard now also requires **at least 3 interest
tags** before letting a student continue — even a correctly-tuned model can't
reliably resolve 13 classes from 1-2 tags, and that's an honest signal-strength
limit, not something more tuning can fix. Verified afterward: single-domain
interest selections (Healthcare, Agriculture, Sports, Technology, Design,
Education) with a realistic 3-tag selection each correctly rank their true
domain #1, several by a wide margin.

**The general lesson, if this class of bug ever resurfaces:** don't assume
it's a feature-weighting problem. Check the dataset's row balance across
classes first (`df["domain"].value_counts()`) — an imbalanced training set
produces a "wins by default" bias that no amount of blend-weight tuning can
fix, because the bias lives in the data, not the combination logic.

## Known limitations (be ready to discuss these, don't hide them)

- All data is synthetic — explicitly labeled as such everywhere it appears.
- Specialization "relevance" is similarity-based on a fairly small number of
  real (synthetic) students per specialization (25-40) — real deployment would
  want more.
- The "add your own interest" free-text field is captured but not yet wired
  into any review/promotion pipeline — that's a designed next step, not an
  oversight.
- Tool-skill self-assessment isn't collected in the wizard (defaults to 0/no
  exposure for everyone) — intentional, since nobody has a meaningful
  self-rating for a tool they haven't started learning yet.
